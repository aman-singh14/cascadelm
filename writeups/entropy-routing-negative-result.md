# Token Entropy Does Not Predict Task Difficulty for Coding-Agent Queries

**A negative result.**

## Summary

CascadeLM was built on the hypothesis that a cheap model's **mean token entropy**
can decide when to escalate a query to a more expensive model. Across 170
grounded coding-agent queries and two probe models, the hypothesis does not hold.

| Measure | Value | Interpretation |
|---|---|---|
| Spearman ρ(entropy, tier) | **+0.085** | no monotonic relationship |
| AUC — escalate (T2+T3) vs T1 | **0.592** | weak (0.5 = chance) |
| AUC — T3 vs T1 | **0.516** | coin flip |
| AUC — T3 vs T2 | **0.408** | *below* chance — inverted |
| Best binary accuracy | **71%** | vs 68% always-escalate base rate |

The best threshold a sweep could find was 0.020 — low enough that it classifies
nearly everything as "escalate." The classifier did not find a boundary; it
defaulted to the majority class.

**Mechanism:** mean token entropy measures how *fluently the probe generates
text*, not how *hard the task is*. These come apart badly on open-ended coding
work.

---

## Hypothesis

An LLM's token-level uncertainty should rise on tasks beyond its competence. If
so, running a cheap model first and measuring the mean Shannon entropy of its
output tokens gives a free routing signal:

```
entropy < T1        -> cheap model's answer is fine
T1 <= entropy < T2  -> escalate to a mid-tier model
entropy >= T2       -> escalate to a strong model
```

This is attractive because the signal is a byproduct of a call you were making
anyway.

## Setup

**Corpus.** 170 synthetic coding-agent queries generated by `gpt-4o`, grounded in
[`fastapi/full-stack-fastapi-template`](https://github.com/fastapi/full-stack-fastapi-template)
at commit `cd83fc1`. Each query is a full OpenAI `messages` array simulating a
real agent turn: a system prompt, a user request, an assistant turn that reads a
file, and the file's verbatim contents as a tool result.

Queries span 10 `phase × complexity` combinations (polish, debugging,
implementation, planning × simple, moderate, complex). To prevent the generator
collapsing onto one scenario, each combination draws from a list of hand-written
scenario seeds, and the full source files are embedded in the generator prompt so
`ground_truth` identifiers are copied from real code rather than invented.

Each query carries an `expected_tier` label (1/2/3) assigned from its
phase/complexity combination.

**Probes.** Two models on Vertex AI:
- `gemini-2.5-flash-lite` — cheapest logprob-capable model
- `gemini-2.5-flash` — stronger, better-calibrated

**Signal.** Mean per-token Shannon entropy, computed over the top-5 logprobs at
each generated position:

```
H_token = -Σ p·ln(p)   over the top-5 candidates
H_mean  = mean(H_token) across all generated tokens
```

---

## Experiment 1 — Weak probe (`flash-lite`), n=149

Every single query routed to Tier 1. Nothing escalated at thresholds
`T1=0.3, T2=0.6`.

| Expected tier | Mean entropy |
|---|---|
| T1 (polish) | 0.097 |
| T2 (debugging) | 0.110 |
| T3 (complex) | 0.110 |

All values fell below 0.30. The distributions overlap almost entirely.
(21 queries errored — see *Incidental findings*.)

## Experiment 2 — Is `mean` the wrong aggregation? n=9

If uncertainty is concentrated in a few pivotal tokens, the mean would dilute it
across hundreds of trivially-predictable ones. Tested mean, max, and p90:

| Expected tier | mean | max | p90 |
|---|---|---|---|
| T1 | 0.013–0.342 | 1.17–1.39 | 0.00–1.05 |
| T2 | 0.073–0.257 | 1.24–1.35 | 0.14–0.92 |
| T3 | 0.053–0.068 | 1.44–1.54 | 0.08–0.20 |

No aggregation separates the tiers. `max` is saturated near 1.2–1.5 for
everything — in any long generation there is always at least one uncertain token.
Notably T3 had the *lowest* mean entropy while emitting 700–5395 tokens: the weak
probe confidently generates long, plausible-looking implementations for the
hardest tasks.

## Experiment 3 — Calibrated probe (`gemini-2.5-flash`), n=170

A 9-query pilot with the stronger probe looked promising (T1 0.035–0.101 vs
T2/T3 0.120–0.833), so we ran the full corpus. **The apparent separation did not
survive at n=170.**

| Expected tier | n | median | mean | sd | IQR |
|---|---|---|---|---|---|
| T1 | 55 | 0.068 | 0.111 | 0.101 | [0.040, 0.183] |
| T2 | 90 | 0.129 | 0.157 | 0.115 | [0.047, 0.265] |
| T3 | 25 | **0.062** | 0.097 | 0.080 | [0.049, 0.088] |

**The ordering is non-monotonic.** T3 — the hardest queries — has a *lower*
median entropy than T2, and is indistinguishable from T1.

Threshold suggestion by adjacent-median midpoint produced `T1=0.099, T2=0.096`,
i.e. `T2 < T1` — a degenerate, unusable configuration.

Discrimination, measured properly:

| Comparison | AUC |
|---|---|
| escalate (T2+T3) vs T1 | 0.592 |
| T2 vs T1 | 0.613 |
| T3 vs T1 | 0.516 |
| **T3 vs T2** | **0.408** |

Only the T1/T2 boundary carries any signal, and it is weak. For T3 the signal is
absent (0.516) or **actively inverted** (0.408) — entropy points the wrong way for
the queries that most need escalation. **15 of 25 T3 queries fall below the T1
median.**

---

## Why it fails

Mean token entropy measures **generation fluency**, not **task difficulty**.
These correlate in some domains and come apart sharply here:

- **Open-ended planning reads as easy.** Asked to design a caching layer, the
  model fluently produces a plausible high-level plan. Each token is easy to
  predict from the last. Low entropy, hard task.
- **Fiddly local edits read as hard.** Asked to fix an off-by-one in a specific
  function, the model hesitates over exactly which line and which operator —
  genuine token-level branching. High entropy, easy task.

That is the inversion visible in the T3-vs-T2 AUC of 0.408. Entropy tracks
*how constrained the next token is*, and open-ended generation is
under-constrained in a way that has nothing to do with whether the answer is
correct.

A weak probe compounds it: `flash-lite` doesn't know what it doesn't know, so it
produces confident text for tasks it has no chance of completing correctly. The
stronger probe hesitates more honestly on mid-difficulty tasks (the one place any
signal appears) but still sails confidently through hard open-ended ones.

## Threats to validity

Stated plainly, because they bound the claim:

1. **The tier labels are asserted, not measured.** `expected_tier` was assigned
   from the phase/complexity combination, not from any observation of whether a
   cheap model actually failed. A perfect difficulty detector would not
   necessarily match these labels. **This is the most serious limitation** and
   motivates the follow-up work below.
2. **Single grounding repository.** One FastAPI template. Entropy behaviour on
   other codebases, languages, or paradigms is unmeasured.
3. **Synthetic queries.** Generated by `gpt-4o` to look like agent turns, not
   captured from real agent sessions.
4. **Two probes, one family.** Both Gemini. A different family (or a model
   explicitly trained for calibration) could behave differently.
5. **Only three aggregations tested.** mean/max/p90. First-N-token entropy, or
   entropy restricted to semantically-pivotal positions, remain untested.
6. **Class imbalance.** T3 has only 25 examples; its statistics are the least
   stable of the three.

## What this does and does not rule out

**Ruled out** (for this corpus): mean/max/p90 token entropy from a Gemini probe as
a threshold-routing signal for coding-agent queries. The AUCs are near chance and
the tier ordering is non-monotonic. No amount of threshold tuning fixes a signal
that isn't ordered.

**Not ruled out:**
- Entropy in narrower domains (classification, short factual QA), where the
  literature is more favourable.
- **Explicit** confidence signals — a model *trained* to report when it is likely
  wrong (e.g. via abstention-aware RL) emits a semantic signal, not a statistical
  byproduct of decoding. Different mechanism entirely.
- Prompt-embedding classifiers — difficulty may be predictable from the query
  text before any generation occurs.
- Internal-activation probes — mid-layer representations are reported to predict
  correctness better than output logprobs do.

## Follow-up

The label limitation is the first thing to fix. Rather than asserting difficulty
from a template, **measure** it: run cheap and strong models on every query, have
a judge compare the outputs, and label a query "hard" only when the strong model
was meaningfully better. That yields an empirical target — *predict whether the
cheap model will fail* — against which entropy, prompt embeddings, trained
confidence, and activation probes can all be compared on equal footing.

## Incidental findings

- **`MALFORMED_FUNCTION_CALL` (21/170 queries).** Sending OpenAI-format
  `tool_calls`/`tool` turns to Vertex as `function_call`/`function_response` parts
  *without declaring the tool schema* makes Gemini attempt its own malformed
  call. It returns no text and no logprobs. Fixed by flattening tool turns to
  plain text (`cascadelm/vertex_format.py`).
- **A failed probe must escalate, not default.** When logprobs are absent there is
  no confidence signal; treating that as "low entropy" would serve an empty
  response as a confident answer.
- **Model availability is region-specific.** Gemini 3.x models resolve in
  `global` but 404 in `us-central1`. Because nothing escalated in the first run,
  this bug stayed hidden until escalation was exercised.
- **Pilot studies on n=9 can invert at n=170.** The stronger probe's apparent
  tier separation vanished on the full corpus. Cheap pilots are for catching
  plumbing errors, not for confirming hypotheses.
